# Data

**Status:** Draft. Decisions: D41, D52–D55. Columns are written in build mode; this doc fixes where data lives, its keys, and retention.

## Stores

| Store | Holds | Hot path waits on it? |
|---|---|---|
| Postgres | Users, wallets, follows, orders + firings, nonce ledger, positions, token metadata, trailing highs | No: engine/execution cache in memory, write in background |
| ClickHouse | Swaps, pool events, candles, backfill, routing logs, execution outcomes | No |
| Kafka | All engine and execution output | No (publish is async) |
| Object storage | Engine snapshots; archived input log (D54): `inputs/<chain>/<core instance>/<first seq>.pb` segments of length-delimited `InputRecord`s plus a `manifest` with the record count, bucket `omnimarket-inputs` in dev; write-once audit log copy (D55) | No |

## ClickHouse and reorgs

- Key: (chain, block hash, log index). Re-inserts are harmless → restartable backfills (D15).
- Status per row: provisional → confirmed → final, or removed. Versioned inserts; `ReplacingMergeTree` keeps the latest.
- Candles: built live from `trades.<chain>` by the candle service; rebuilt for windows touched by corrections. 1s candles are also a recovery input (D39). For the demo the API builds them in memory instead (D96, D103), from `trades.<chain>` and `trade-history.<chain>`, at every `CandleInterval` in the API contract: 1s, 1m, 5m, 15m, 1h, 4h and 1d (#124; the terminal's chart offers 15m, 4h and 1D). How they're priced is under the `candles` topic below.

## API topics (WebSocket)

What the API serves to both UIs (D62, D91), defined in `proto/omnimarket/api/v1/stream.proto`. These are subscription topics on the API's WebSocket, built from the Kafka topics above by the API's read models; they aren't Kafka topics. v0 is Base-only, so they carry no chain.

| Topic | Snapshot | Deltas, and their key |
|---|---|---|
| `status` | `EngineStatus`, sent once the engine's first status arrives | `EngineStatus`, replacing the last |
| `discovery` | `DiscoveryFeed` | `DiscoveryRow` (by token), `DiscoveryRowRemoved` |
| `token:<address>` | `TokenSnapshot` | `TokenTick`, at most 20 a second (D43) |
| `trades:<address>` | `TradeList`, newest first | `Trade`, appended; natural key (chain, block hash, log index) |
| `candles:<address>:<interval>` (`1s`, `1m`, `5m`, `15m`, `1h`, `4h`, `1d`) | `CandleSeries`, oldest first | `Candle` (by open time) |
| `account` (needs the session token) | `AccountSnapshot` | `Account`, `Position` (by token), `Quote` (re-quotes), `TradeStatus` and `TradeReceipt` (by trade ID), `Order` and `OrderStatus` (by order ID), `Firing` (by firing ID) |

**`discovery` (#81, `crates/api/src/discovery.rs`).** Built from `pool-updates.base`, `trades.base` and `prices.base`. One row per token, keyed by its address:

- **New:** tokens with a pool created during the session, newest creation block first, for the new-pool window (`--new-pool-window-ms`, default 1h). A pool counts as created when the engine discovers it empty (v2 reserves of zero, or a v3 pool not yet initialized); one first seen with state predates the engine's start and is never new. Its token is learnt from the first trade or price record that names the pool, in either order. The row's pool is the new pool; its creation time is the block's distance from the head × 2s (Base's fixed block time).
- **Trending:** tokens with a display price, at least `--trending-min-depth-usd` of ±2% depth (default $10,000, D24) and a trade in the last 5m, ranked by 5m USD volume, then 5m txns, then address. A trade's USD volume is its token amount at the token's display price before its block's price records apply (the previous priced block's); a trade before the token's first price counts as a txn with no volume.
- **Rows** carry the window stats (5m, 1h, since tracking began; the price change is against the newest price at or before the window's start), the main pool's price, depth and market cap, `lists`, and `rank`: the row's place in Trending if it trends, otherwise in New. Each list holds at most 100 rows. Safety is empty until #89.
- **Merged in a fixed order.** The consumer reads the three topics interleaved however Kafka hands them over, so the read model doesn't take records as they come. Each topic has one partition, so its own order is fixed, though not quite block order: the engine publishes a pool, and its trades, once it has proven or read the pool, up to tens of blocks (25 in the pinned recording) after the block it was seen in. Each record is placed at its topic's position when it arrives (the highest block that topic has reached), and once all three topics have passed position N, position N's records are applied: pool updates, then trades, then prices, each in its topic's order. The output is then the same for any interleaving, including a restart that reads one topic far ahead of the others (`the_discovery_feed_is_the_same_however_the_topics_interleave`). A topic that goes quiet holds the feed until it moves again; on Base every block moves all three.
- **Deltas, once per block.** Once every topic has passed a block, the rows as of that block are ranked and compared with those last published: a changed row goes out as a `DiscoveryRow`, a row that left both lists as a `DiscoveryRowRemoved`. So a new pool appears once every topic reaches the next block, a row whose rank and data don't change isn't sent, and ties break by address, so the order holds while ranks do. The snapshot and `GET /v1/discovery` serve the published rows, so a delta is always newer than its snapshot.
- **Filters** (`GET /v1/discovery?list=new|trending&min_depth_usd=&max_age_ms=`), server side: a list, a minimum depth, and a maximum pool age, which drops rows whose pool age isn't known. A value that doesn't parse is a 400.

**`candles:<address>:<interval>` (#80, D103, `crates/api/src/candles.rs`).** Built from `trades.base` and `trade-history.base`, with `prices.base` for each token's decimals and pools. Also served as `GET /v1/candles` (frontend.md).

- **Exact per pool.** Each pool has a candle per interval and open time, in its quote asset: open and close from the trades with the lowest and highest (block, log index), high and low from the raw prices (D102), volume summed in quote base units, and a count of trades. A trade counts once, by (block hash, log index), however often it arrives: live, from history, or both after an engine restart. So the candles are the same for any order the topics are read in (`candles_rebuilt_from_a_recorded_session_match_the_live_ones`). Candles open on multiples of their length since the Unix epoch, so 1d opens at midnight UTC, and one is closed once a later trade's block time is past its end. A trade with no price (it moved none of the token) counts as a trade and volume, not a price.
- **Priced in USD when served.** A token's candle merges its pools counted toward its display price in its latest price update, or its main pool when none is (thin, D18), keeping only pools that trade it against a quote asset. A raw price becomes USD with the token's decimals (from the price update's metadata; a token without them has no candles) and the quote's: USDC and USDT are $1, and WETH is WETH's own candle's USD close at the same interval and open time, or its nearest earlier, or its nearest later, passing over any WETH candle whose trades have no price. Open is the merged pools' earliest trade, close their latest; volume and trades add up across them.
- **And in the quote asset (#149).** Each candle also carries a quote view in the quote asset of the token's main pool (D18), as of its latest price update: the asset's address and symbol, and the candles of the merged pools quoted in that asset, merged again. Pools quoted in another asset are left out of this view, so it needs no USD conversion and doesn't depend on WETH's candle. Open, high, low and close come from the raw prices and volume from quote base units, exactly as decimal strings, with `quote_trades` counting the trades in it. The view is empty until the main pool has traded.
- **Snapshot and deltas.** The snapshot is the newest 1,440 candles (a day of 1m), oldest first, or an empty series. A live trade sends the candle it changed at each interval, as of the count of trades counted, so one a snapshot already counted is skipped. History sends no deltas: a token that took history gets a fresh snapshot on each of its candle topics with the next live trade. A candle already sent changes without a delta when the token's counted pools change, or WETH's close moves; the next snapshot has it.
- **Lineage.** A candle's ID is from the natural key (chain id u64, token 20 bytes, interval length in ms u64, open time u64, its latest trade's ID), kind `candle`, caused by that trade; a series', kind `candle_series` (chain, token, interval length, then each candle's ID), is caused by its newest candle.

Each subscription gets a snapshot, then deltas numbered by a per-topic `seq`; a gap means resubscribe. The server may send a topic a fresh snapshot at any point, restarting `seq` at 0: when a connection falls too far behind, or when a candle topic takes history. Every record carries its lineage: a message presenting one backend record carries that record's lineage, and one the API assembles (a snapshot, list or feed) carries its own, caused by what it was built from.

## Records and lineage IDs (D71)

Every wide event carries `omnimarket.lineage.v1.Lineage { id, caused_by[] }`, with 16-byte IDs. A record with a natural key takes `LineageId::from_natural_key(kind, key)`: BLAKE3 over the kind (length-prefixed) and the key fields, fixed-width little-endian in the order listed, cut to 128 bits. A record without one takes two draws from the core's seeded Rng, so replay reproduces it.

| Record | Schema | Kind | Natural key | Caused by |
|---|---|---|---|---|
| Input-log record | `omnimarket.det.v1.InputRecord` | (none: an input, not a wide event) | (core instance, seq) | |
| Toy swap (M0 demo) | `omnimarket.sim.v1.ToyEvent` | `sim.toy_event` | id (u64) | |
| Toy quote (M0 demo) | `omnimarket.sim.v1.Quote` | | none: seeded Rng | |
| Toy decision (M0 demo) | `omnimarket.sim.v1.ToyDecision` | `sim.toy_decision` | event id (u64) | the swap, then the quote |
| Chain event | `omnimarket.chain.v1.Log` (inside `Block`) | `chain_event` | chain id (u64), block hash (32 bytes), log index (u64) | |
| Pool update | `omnimarket.pool.v1.PoolUpdate` | `pool_update` | chain id (u64), pool (20 bytes), block hash (32 bytes), log index (u64) | the chain event |
| Trade | `omnimarket.trade.v1.Trade` | `trade` | chain id (u64), block hash (32 bytes), log index (u64) | the chain event (the Swap log) |
| Engine status | `omnimarket.status.v1.EngineStatus` | `engine_status` | chain id (u64), block hash (32 bytes) | (none: a block has no lineage ID of its own) |
| Price update | `omnimarket.price.v1.PriceUpdate` | `price_update` | chain id (u64), token (20 bytes), block hash (32 bytes) | the latest update of each pool it was priced from, then the native token's price update if a pool quotes in it (sorted by ID) |

Chain events will key on (chain, block hash, log index), firings on the firing ID (D35) and intents on their hash, as each schema lands.

## Observability data (D53–D55)

- **Lineage edges** (cause ID → effect ID, with type and timestamp) in ClickHouse; money paths 100%.
- **Decision records** (alternatives, scores, reasons, config version, brake state) in ClickHouse, 1 year.
- **Audit log:** hash-chained, append-only, ClickHouse + write-once Cloud Storage; daily root anchored on Base. Kept forever.

## Privacy (D52)

Telemetry uses pseudonymous user IDs. Per-user records are encrypted with a per-user key; deleting the key makes them unreadable (crypto-shredding) while the audit log's hash chain stays verifiable.

## Snapshots

Versioned, compressed binary per chain every ~30s (D40); last 10 kept. RustFS in dev/staging (D75); Cloud Storage in production (D51).

## Retention

Candles forever. Raw swaps from the 30-day backfill onward; downsample past 90 days if needed.
